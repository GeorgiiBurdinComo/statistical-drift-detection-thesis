\chapter{Introduction}

\section{Context and Motivation}
Industrial classification pipelines increasingly rely on Large Language Model (LLM) providers that expose their systems through application programming interfaces. In such settings, the deployed model can be viewed as a non-stationary black-box function $f_t(x)$ whose internal parameters and update schedule are controlled by the provider rather than by the user. As a result, the behaviour of the same API-accessible model may change over time even when the downstream task, the prompt, and the evaluation procedure remain fixed~\cite{chen2023chatgpt,tu2023chatlog,echterhoff2024muscle}.

The practical motivation for this thesis arises from the author's two-year work experience at \textbf{Gocomo GmbH}. In the company's social-media analytics workflow, LLMs are used in batch mode to determine whether a post is relevant to a specified campaign, brand, event, or other marketing entity. This is naturally formulated as a binary classification task. Because the volume of incoming content is large, manual verification is not scalable, and automated classification becomes a necessary operational component.

However, the use of external LLM APIs creates a reliability problem. A model that performs well during an initial benchmark may later degrade due to silent provider-side updates. In a business-critical pipeline, such degradation must be detected early. At the same time, repeated full-scale benchmarking on a large labelled dataset is costly. This creates a need for a monitoring methodology that is statistically informative, operationally feasible, and economically justified.
\section{Problem Statement}
This thesis addresses the problem of how to evaluate and monitor API-based LLM classifiers in a production environment where model behaviour may change over time. The central challenge is that the user does not control the underlying model updates, yet must still make reliable deployment decisions based on observed task performance.

More specifically, the problem consists of four interconnected parts:
\begin{enumerate}
    \item The social-media relevance detection task must be formalised in a way that permits consistent evaluation across models, prompts, and time points.
    \item Because repeated evaluation on the full reference benchmark is economically expensive, a smaller monitoring subset must be constructed without losing the ability to detect practically relevant performance changes.
    \item A statistical rule is required to distinguish variability in performance from genuine model drift.
    \item Once multiple candidate models are monitored, deployment decisions must account not only for predictive performance but also for inference cost.
\end{enumerate}

In addition, if a deployed model exhibits degraded performance, it is natural to ask whether this degradation can be mitigated without immediately replacing the model. This motivates the investigation of prompt optimisation as an adaptive mechanism within the monitoring framework.

Accordingly, the thesis does not study model drift merely as an observational phenomenon. Its objective is to develop a practically usable framework for benchmark design, drift-sensitive monitoring, cost-aware model selection, and post-drift adaptation for binary classification with black-box LLM APIs.
\section{Research Questions}
The problem stated above is investigated through the following research questions:

\begin{enumerate}
    \item[\textbf{RQ1:}] How can the campaign-relevance detection task be formally represented as a binary classification problem for non-stationary black-box LLM APIs?

    \item[\textbf{RQ2:}] How can a reduced monitoring subset be derived from a larger reference benchmark so that routine evaluation remains substantially cheaper while preserving sensitivity to model drift?

    \item[\textbf{RQ3:}] Which statistical criteria and alerting rules are appropriate for detecting practically significant performance degradation over time?

    \item[\textbf{RQ4:}] How should candidate models be compared and selected when deployment decisions depend on both predictive quality and inference cost?

    \item[\textbf{RQ5:}] To what extent can prompt optimisation improve or recover task performance after drift has been detected, and how can such optimisation be integrated into the monitoring loop?
\end{enumerate}

\section{Formal Task Definition}

\subsection{The Probability Space}
Let $\mathcal{X}$ denote the input space of social-media posts (textual content and associated metadata) and let $\mathcal{Y} = \{0, 1\}$ be the label space, where $1$ indicates relevance to a campaign and $0$ indicates irrelevance. We assume that pairs $(x, y)$ are drawn from a joint distribution $P_t$ on $\mathcal{X} \times \mathcal{Y}$. The subscript $t$ signifies that this distribution or the underlying labeling function may evolve over time.

\subsection{LLM as a Parameterized Conditional Distribution}
In the context of LLM-as-a-Service, the model is a "black box." We define the classifier as a function $f$:
\begin{equation}
    f(x; \pi, \theta_t) \to \hat{y} \in \{0, 1\}
\end{equation}
where:
\begin{itemize}
    \item $\pi \in \mathcal{P}$ represents the \textbf{prompt}, a discrete string chosen from the space of all possible instructions $\mathcal{P}$.
    \item $\theta_t$ represents the \textbf{frozen model weights} provided by the API at time $t$. We do not have access to $\theta_t$, but we observe its outputs.
\end{itemize}
The model's output can be viewed as an approximation of the conditional probability $P(Y|X, \pi; \theta_t)$.

\subsection{Loss Function and Risk}
To quantify performance, we define a loss function $\mathcal{L}: \mathcal{Y} \times \mathcal{Y} \to \mathbb{R}$. For this binary classification task, we utilize the zero-one loss:
\begin{equation}
    \mathcal{L}(\hat{y}, y) = \mathbb{I}(\hat{y} \neq y) = 
    \begin{cases} 
      1 & \text{if } \hat{y} \neq y \\
      0 & \text{if } \hat{y} = y 
    \end{cases}
\end{equation}

The \textbf{Expected Risk} (or generalization error) at time $t$ for a fixed prompt $\pi$ is:
\begin{equation}
    R(f_{\pi, \theta_t}) = \mathbb{E}_{(x,y) \sim P_t} [\mathcal{L}(f(x; \pi, \theta_t), y)]
\end{equation}

Since $P_t$ is unknown, we estimate the risk using the \textbf{Empirical Risk} $\hat{R}$ over a finite dataset $\mathcal{D}$ of size $n$:
\begin{equation}
    \hat{R}(f_{\pi, \theta_t}; \mathcal{D}) = \frac{1}{n} \sum_{i=1}^{n} \mathcal{L}(f(x_i; \pi, \theta_t), y_i)
\end{equation}
Model drift is therefore defined as a statistically significant increase in $R(f_{\pi, \theta_t})$ over time $t$ for a fixed prompt $\pi$.
The expected risk \(R(f_{\pi,\theta_t})\) represents the true average loss of the classifier under the unknown data-generating distribution \(P_t\). In the present binary classification setting with zero-one loss, this quantity is equal to the probability of misclassification. Since the underlying distribution \(P_t\) is not directly observable, the expected risk cannot be computed exactly in practice.

Instead, performance is estimated through the empirical risk \(\hat{R}(f_{\pi,\theta_t};\mathcal{D})\), which is the average loss over a finite labelled dataset \(\mathcal{D}\). Under zero-one loss, the empirical risk is simply the fraction of incorrectly classified examples in the dataset. Thus, empirical risk serves as a sample-based approximation of expected risk and forms the basis for all practical evaluation and monitoring procedures in this thesis.

\section{The Monitoring Subset}
To reduce operational costs, we construct a monitoring subset. Crucially, this is not a naive uniform random sample. It is an \emph{informative} subset heavily weighted towards instances where models historically disagreed. Because it over-indexes on edge cases, it acts as a stress test. While it may not provide an unbiased estimate of global accuracy, it is highly sensitive to model drift. 

\subsection{Sample Size Determination via Annotation Noise Floor}
The exact size of the monitoring subset, $n=300$, is not arbitrary but is derived from the inherent noise floor of the human annotation process. In complex subjective tasks such as social-media campaign relevance, human inter-annotator disagreement establishes an irreducible error rate, generally estimated at $\epsilon \approx 0.05$ ($5\%$).
\textcolor{red}{\textbf{NB!:}  show an example of a disagreement between two human annotators.}
Consequently, any model performance fluctuation smaller than $\epsilon$ is statistically indistinguishable from background label noise. The monitoring system must therefore be calibrated to achieve a Minimum Detectable Effect (MDE) of $\Delta = 0.05$. For an observed drop to trigger a valid alert, the margin of error of our empirical accuracy estimate $\hat{A}_n$ must be strictly bounded by this noise floor.

Let $Z_{1-\alpha}$ be the critical value for a one-sided hypothesis test at significance level $\alpha = 0.05$, where $Z_{0.95} \approx 1.645$. To ensure that the margin of error does not exceed our threshold $\Delta$, the required sample size $n$ must satisfy:
\begin{equation}
    Z_{1-\alpha} \sqrt{\frac{A(1-A)}{n}} \le \Delta
\end{equation}

Because $\mathcal{D}_n$ is explicitly constructed from the region of maximal model disagreement, the empirical accuracy is pushed toward the maximum-entropy state, $A \approx 0.5$. This represents the absolute worst-case variance scenario for a Bernoulli process, where $A(1-A) = 0.25$. Substituting these values yields:
\begin{equation}
    1.645 \sqrt{\frac{0.25}{n}} \le 0.05
\end{equation}
\begin{equation}
    \frac{0.8225}{\sqrt{n}} \le 0.05 \implies \sqrt{n} \ge 16.45
\end{equation}
\begin{equation}
    n \ge 270.6
\end{equation}
\begin{remark}
    The use of the Normal approximation ($Z_{0.95}$) assumes that each of the 300 observations is independent and identically distributed (i.i.d.) within the subpopulation of high-disagreement cases. Although the monitoring subset $\mathcal{D}_n$ is intentionally biased compared to the general dataset $\mathcal{D}_N$, the Central Limit Theorem still ensures that the sampling distribution of the sample accuracy $\hat{A}_n$ will converge towards normality as sample size increases. Assuming $A=0.5$ corresponds to adopting a \emph{Maximum Entropy} prior, yielding the most conservative estimate for the required sample size given uncertainty about the true error rate in these edge-case examples.
\end{remark}
To ensure adequate statistical power, the theoretical minimum sample size $n \geq 271$ is voluntarly rounded up to $n=300$. This demonstrates that a monitoring subset of 300 samples is the minimum required to reliably detect a $5\%$ drop in performance attributable to model drift, even in the presence of human annotation noise, thus justifying the use of $n=300$ under worst-case assumptions.

\subsection{Informative Sampling via Model Disagreement}
The monitoring subset was constructed by selecting instances where at least one model in the initial benchmark exhibited disagreement. Let $y_i$ be the ground truth and $\hat{y}_{i,m}$ be the prediction of model $m \in \mathcal{M}$. The subset $\mathcal{D}_{300}$ is defined as:
\begin{equation}
    \mathcal{D}_{300} \subset \{ x_i \in \mathcal{D}_{1200} \mid \exists m_j, m_k \in \mathcal{M} : \hat{y}_{i,m_j} \neq \hat{y}_{i,m_k} \}
\end{equation}

This approach is grounded in the principles of \emph{Active Learning}, specifically \emph{Uncertainty Sampling}. By focusing on the disagreement region, we sample from the portion of the manifold where the models' posterior probabilities $P(Y|X)$ are closest to the decision threshold.

\subsection{Sensitivity and Statistical Power}
From a hypothesis testing perspective, the goal of weekly monitoring is to reject the null hypothesis $H_0: \Delta A = 0$ (no drift). The statistical power of a test—the probability of detecting drift when it exists—is higher on instances with high prediction variance. 

In the full dataset ($N=1200$), a large portion of instances are "easy" cases with $P(Y=1|X) \approx 1$ or $0$. On these instances, the Bernoulli variance $p(1-p)$ is minimal, making them "robust" to small model drifts. In contrast, the disagreement subset ($n=300$) centers the evaluation on the "hard" cases where $p \approx 0.5$. 

While $\hat{A}_{300}$ is a biased estimator of the global population accuracy, it serves as a \textbf{proxy metric} with higher sensitivity. A performance drop of $5\%$ on the hard 300-sample subset is a leading indicator of degradation that would require a much larger (and more expensive) sample to detect on the full 1200-sample distribution. Thus, $n=300$ provides an optimal balance between inference cost and the statistical power to detect model updates.
\section{Theoretical Justification of Disagreement Sampling}

The construction of the monitoring subset $\mathcal{D}_{300}$ via model disagreement represents a deliberate departure from simple random sampling (SRS). In this section, we formalise this approach through the lenses of \emph{importance sampling} and \emph{active learning}.

\subsection{Selection Bias and the Sampling Indicator}

Let $S_i \in \{0, 1\}$ be a Bernoulli random variable indicating whether the $i$-th instance from the reference benchmark $\mathcal{D}_{N}$ is included in the monitoring subset $\mathcal{D}_{n}$. Under SRS, $P(S_i = 1) = n/N$. In our framework, the inclusion probability is conditioned on the disagreement of a model ensemble $\mathcal{M}$:
\begin{equation}
    P(S_i = 1 \mid x_i, \mathcal{M}) = q_i,
\end{equation}
where $q_i$ is high if the models in $\mathcal{M}$ yield conflicting predictions $\hat{y}_{i,m}$.

Consequently, the empirical accuracy on the subset, $\hat{A}_n$, is a \textbf{biased estimator} of the population accuracy $A_N$:
\begin{equation}
    \mathbb{E}[\hat{A}_n] \neq A_N.
\end{equation}
This bias arises because $\mathcal{D}_n$ intentionally over-represents ``hard'' cases near the decision boundary, for which the expected accuracy is lower than the population average.

\subsection{Change of Measure and the Horvitz--Thompson Estimator}

To reconcile the subset performance with the population mean, we can apply a \textbf{change of measure}. From the theory of \emph{importance sampling}, an unbiased estimate of $A_N$ can be recovered by weighting each observation by the inverse of its inclusion probability.

Let $q_i = P(S_i = 1 \mid x_i, \mathcal{M})$ denote the (possibly model-dependent) inclusion probability. The Horvitz--Thompson estimator of the population accuracy is
\begin{equation}
    \hat{A}_{\mathrm{HT}} = \frac{1}{N} \sum_{i \in \mathcal{D}_n} \frac{\mathbb{I}(\hat{y}_i = y_i)}{q_i},
\end{equation}
where the factor $1/q_i$ serves as an \textbf{importance weight}. In principle, this restores unbiasedness with respect to the original reference distribution. In practice, our production pipeline treats $\hat{A}_n$ primarily as a \emph{monitoring signal}, but the existence of $\hat{A}_{\mathrm{HT}}$ clarifies the statistical relationship between the curated subset and the underlying data-generating distribution.

\subsection{Bias–Power Trade-off in Drift Detection}

The motivation for accepting selection bias lies in a deliberate \textbf{bias–power trade-off}. For drift detection, the primary objective is not to obtain a perfectly calibrated estimate of global accuracy, but to maximise the \emph{power} of a test for changes over time.

By concentrating on the high-entropy region around the decision boundary, we sample from those $x \in \mathcal{X}$ where the classifier is intrinsically uncertain and where small perturbations of the underlying model parameters $\theta_t$ are most likely to flip predictions. Intuitively, these are the points where the gradient of the loss with respect to $\theta_t$ is largest; small, otherwise imperceptible shifts in $\theta_t$ that would be masked by ``easy'' examples in $\mathcal{D}_{N}$ are amplified in $\mathcal{D}_n$.

Formally, we trade interpretability of $\hat{A}_n$ as a population accuracy for increased sensitivity of the drift signal:
\begin{enumerate}
    \item \textbf{Bias Increase:} $\hat{A}_n$ systematically underestimates $A_N$ because it is evaluated on a stress-test subset.
    \item \textbf{Power Increase:} For a fixed evaluation budget $n$, the test statistic based on $\mathcal{D}_n$ has higher power to detect changes in accuracy than one based on an SRS of the same size, since it concentrates mass on inputs with high prediction variance.
\end{enumerate}
In this sense, $\mathcal{D}_n$ is designed as an optimised \emph{diagnostic instrument} for temporal instability, rather than as a representative sample of day-to-day traffic.
\chapter{Drift Monitoring and Model Selection Methodology}

\section{Formalisation of Temporal Evaluation}
Let $t \in \{1, \dots, T\}$ represent weekly evaluation intervals. For each model $m$, we track the empirical accuracy $\hat{A}_t$ on the monitoring subset $\mathcal{D}_{300}$. Because $\mathcal{D}_{300}$ consists of high-disagreement cases, $\hat{A}_t$ will be lower than the accuracy on the full benchmark, but it serves as our primary monitoring signal $S_t$.

\section{Statistical Framework for Drift Detection}
To distinguish between random performance fluctuation and genuine model drift, we utilize a threshold-based alerting rule. 

\subsection{Standard Error on the Informative Subset}
Given that $n=300$, the standard error of our accuracy estimate $\hat{A}_t$ is:
\begin{equation}
    SE(\hat{A}_t) = \sqrt{\frac{\hat{A}_t(1 - \hat{A}_t)}{n}}
\end{equation}
For a model with an expected accuracy of $0.70$ on the hard subset, $SE \approx 0.026$ ($2.6\%$). 

\subsection{The Alerting Rule}
We define a performance drop as statistically significant if the difference between the current accuracy and the baseline accuracy $\hat{A}_0$ exceeds a confidence interval. However, for production stability, we use a \textbf{Practical Drift Threshold} $\tau_{\mathrm{drift}}$. An alert is triggered if:
\begin{equation}
    \hat{A}_t < \hat{A}_{0} - k \cdot SE(\hat{A}_0) - \tau_{\mathrm{drift}}
\end{equation}
where $k$ is a scaling factor (typically $k=2$ for a $\approx 95\%$ confidence interval) and $\tau_{\mathrm{drift}}$ is the minimum degradation the business is willing to tolerate before intervening.

\section{Accuracy--Cost Trade-off Modeling}
Model selection is formulated as a multi-objective optimization problem. We define the \textbf{Operational Value Score} $V_t(m)$:
\begin{equation}
    V_t(m) = \frac{\hat{A}_t(m)}{C(m)^\alpha}
\end{equation}
where $C(m)$ is the cost per 1,000 requests and $\alpha$ is a sensitivity parameter. 
\begin{itemize}
    \item If $\alpha=0$, we select purely based on accuracy.
    \item If $\alpha=1$, we select based on "accuracy per dollar."
\end{itemize}
In our workflow, we set $\alpha$ based on the current budget constraints of the Gocomo pipeline.

\section{Decision Logic for Model Switching}
The system follows a three-step decision tree each week:
\begin{enumerate}
    \item \textbf{Monitor:} Calculate $V_t$ for all candidate models.
    \item \textbf{Detect:} Check if the currently deployed model $m_{curr}$ has triggered a drift alert.
    \item \textbf{Act:} If drift is detected, calculate if another model $m_{alt}$ provides a significantly higher $V_t$. If no model satisfies the threshold, trigger the \textbf{Prompt Optimisation} loop (Chapter 4).
\end{enumerate}
\section{Statistical Drift Detection}
Let $\widehat{A}_t$ be the empirical accuracy of a model on the monitoring subset at week $t$. We define the temporal performance delta as $D_t = \widehat{A}_t - \widehat{A}_{t-1}$. An alert is triggered if the degradation exceeds a practical operational threshold $\tau_{\mathrm{drift}}$:
\begin{equation}
    D_t < -\tau_{\mathrm{drift}}
\end{equation}
This threshold must account for the natural variance of the 300-sample subset to avoid false-positive alerts.

\section{Cost-Aware Model Selection}
Predictive accuracy cannot be isolated from inference cost in a production environment. Let $C_t(m)$ be the inference cost and $A_t(m)$ be the accuracy for model $m$. We define a deployment utility function $J_t$ that penalizes high costs:
\begin{equation}
    J_t(m) = A_t(m) - \lambda C_t(m)
\end{equation}
where $\lambda > 0$ represents the business's willingness to pay for marginal accuracy improvements. The system dynamically selects the model $m^\star = \arg\max_{m} J_t(m)$ each week.

\chapter{Prompt Optimisation as an Adaptive Mechanism}
\section{Integrating Optimisation into the Monitoring Loop}
When a deployed model triggers a drift alert ($D_t < -\tau_{\mathrm{drift}}$), switching to a more expensive model is not the only recourse. We can attempt to recover performance via prompt optimization.

\section{Pareto-Based Prompt Search (GEPA)}
We utilize a reflective evolutionary method (GEPA)~\cite{gepa2025} for prompt adaptation. Because prompt space is discrete and non-convex, greedy selection often fails. Instead, we maintain a candidate pool of prompts and evaluate their per-instance score vectors $\bm{s}(\Pi) = (s_1(\Pi), \dots, s_n(\Pi))$. 

We retain prompts based on Pareto dominance to preserve search diversity. A prompt $\Pi^{(a)}$ dominates $\Pi^{(b)}$ if it performs at least as well on all instances and strictly better on at least one. By mutating prompts on the Pareto frontier using natural-language reflections from execution traces, we can systematically search for a prompt $\Pi^\star$ that maximizes $J_t(m)$ without altering the underlying API model.

\section{Dataset Storage and Trace Logging}
\label{sec:dataset-storage}

All labels and input features for the campaign relevance task are stored in Langfuse as a dedicated dataset.
Each row represents a single influencer post with a stable \texttt{custom\_id}, campaign brief, caption, optional image references, and a boolean \texttt{campaign\_relevant} label.
During evaluation, each model call is recorded as a Langfuse trace whose metadata includes the \texttt{custom\_id}, model name, provider, run identifier, latency, and token usage.
This makes it possible to reconstruct historical evaluations and to filter traces by dataset version, model, or time window when analysing drift.

\section{Batch Evaluation Process}
\label{sec:batch-process}

Batch runs are orchestrated by \texttt{run\_eval.py}, which:
\begin{enumerate}
    \item Loads an evaluation subset via \texttt{load\_dataset\_rows}, either directly from Langfuse or from a CSV export (e.g.\ the disagreement subset).
    \item Applies a shared prompt template to produce a normalised conversational payload (system + user messages) per example.
    \item Calls provider-specific helpers (\texttt{batch\_openai.py}, \texttt{batch\_gemini.py}, \texttt{batch\_claude.py}) that write JSONL request files and submit batch jobs.
    \item Writes a manifest \texttt{data/batch\_ids.json} listing all submitted batch IDs, models, and providers.
\end{enumerate}
GitHub Actions workflows schedule and execute this pipeline: they trigger batch submission, poll job status until completion, and then run the ingestion scripts (\texttt{poll\_and\_ingest.py}, \texttt{ingest.py}) that attach responses to the correct traces in Langfuse.

\section{Interaction with LLM APIs}
\label{sec:llm-api-interaction}

All models are queried via provider-native batch APIs, but the logical payload is always the same: a schema-constrained campaign relevance call built from one labeled example.
Concretely:
\begin{itemize}
    \item \textbf{OpenAI} (\texttt{batch\_openai.py}): writes JSONL lines of the form \{\texttt{custom\_id}, \texttt{method="POST"}, \texttt{url="/v1/responses"}, \texttt{body}\} and submits the file to the OpenAI Batch API with \texttt{endpoint="/v1/responses"}.
    \item \textbf{Gemini} (\texttt{batch\_gemini.py}): writes JSONL lines with a \texttt{request} object (contents, optional \texttt{systemInstruction}, \texttt{generationConfig}) and uploads the file to the Google GenAI batch API via \texttt{client.batches.create(model=..., src=...)}.
    \item \textbf{Claude} (\texttt{batch\_claude.py}): builds an in-memory list of \{\texttt{custom\_id}, \texttt{params}\} records and passes it directly to the Anthropic Messages Batches API via \texttt{client.messages.batches.create(requests=...)}; the streamed batch results are later normalised into JSONL by \texttt{download\_claude\_batch\_results}.
\end{itemize}
In all three cases, the underlying request encodes:
\begin{itemize}
    \item a \texttt{custom\_id} linking back to the dataset row,
    \item a conversational payload (system instructions + user content with campaign brief and post),
    \item and a JSON schema (\texttt{CampaignRelevanceMinimal}) that forces the response into a \{\texttt{campaign\_relevant}, \texttt{relevancy\_reasoning}\} object.
\end{itemize}

\section{Metrics Collection and Monitoring Dashboard}
\label{sec:metrics-dashboard}

The monitoring stack exposes exactly two core metrics: \textbf{classification accuracy} on the monitoring subset and \textbf{inference cost} per model.

Ingestion is handled by the script \texttt{ingest.py}, which processes each batch output file as follows:
\begin{enumerate}
    \item Parse each JSONL line and normalise the provider response (OpenAI, Gemini, Claude) into a common structure.
    \item Extract the boolean \texttt{campaign\_relevant} prediction from the model output.
    \item Look up the ground-truth label for the corresponding \texttt{custom\_id} from Langfuse or a CSV export.
    \item Derive token usage \((\text{input}, \text{output}, \text{total})\) from the provider-specific usage fields.
    \item Convert token usage into a dollar cost using the per-million-token prices in \texttt{config/models.yaml}.
    \item Write a Langfuse trace/span with:
    \begin{itemize}
        \item metadata: \texttt{model}, \texttt{provider}, \texttt{custom\_id}, optional \texttt{run\_id};
        \item the parsed input and raw provider response;
        \item three scores:
        \begin{itemize}
            \item \texttt{accuracy} \(\in \{0,1\}\) (per-trace correctness),
            \item \texttt{error\_type} \(\in\)\{\texttt{true\_positive}, \texttt{false\_negative}, \texttt{true\_negative}, \texttt{false\_positive}\},
            \item \texttt{cost\_usd} (total dollar cost for this trace);
        \end{itemize}
        \item detailed \texttt{usage\_details} and \texttt{cost\_details} for debugging and audits.
    \end{itemize}
\end{enumerate}

On top of this logging layer, a small Streamlit dashboard queries Langfuse and aggregates scores over the 300-example monitoring subset.
The dashboard provides:
\begin{itemize}
    \item per-model accuracy curves over time (mean of the per-trace \texttt{accuracy} scores),
    \item confusion-matrix summaries derived from \texttt{error\_type},
    \item request volume and latency distributions per run,
        \item and cost views such as cost per run and estimated cost per 1,000 inferences.
\end{itemize}
Screenshots from this Streamlit dashboard are used in the experiments chapter to show concrete drift events and the associated accuracy--cost trade-offs.
Together, \texttt{ingest.py} and the dashboard form the practical monitoring surface of the statistical surveillance loop described in the previous chapters.
\chapter{Conclusion}
This thesis provides a statistically grounded, cost-aware framework for the continuous evaluation of LLMs in production. By decoupling the initial reference benchmark from an informative monitoring subset, and pairing statistical drift detection with automated prompt optimization, organizations can maintain high classification performance despite the inherent instability of black-box LLM APIs.
