\chapter{System Implementation}
\label{chap:system-architecture}

This chapter describes the batch evaluation system.
The system stores item-level outputs, scores, and run identifiers,
so completed runs can be rescored, paired, and audited without a new
model call.
Provider APIs return the model outputs.
Local code fixes the datasets, builds requests, scores outputs, and
exports the review views.

\section{System flow}
\label{sec:evaluation-pipeline-overview}
The system has five parts:
\begin{enumerate}
    \item fixed labelled datasets in Langfuse;
    \item request normalization and orchestration;
    \item provider-specific batch adapters;
    \item retrieval, ingestion, and scoring;
    \item a read-only dashboard for review.
\end{enumerate}

Langfuse is the persistent evaluation store.
It holds two fixed labelled datasets:
\begin{enumerate}
    \item the full 1199-item benchmark\\
    \mbox{\texttt{campaign\_relevance\_02e1a68ccb0f}};
    \item the fixed 300-item monitoring panel\\
    \mbox{\texttt{campaign\_relevance\_disagree\_subset\_9d488308aa46}}.
\end{enumerate}
Each dataset item stores:
\begin{enumerate}
    \item the multimodal input;
    \item the expected binary label \texttt{campaign\_relevant};
    \item stable metadata such as \texttt{custom\_id}.
\end{enumerate}
After each run, Langfuse also stores traces and scores for the returned outputs.

Figure~\ref{fig:system-architecture} shows the service architecture:
GitHub Actions runs the pipeline, Langfuse supplies the fixed dataset
and stores traces and scores, provider batch APIs execute inference,
and the Streamlit dashboard reads traces and scores from Langfuse.

These parts support four run types:
\begin{enumerate}
    \item a baseline full-benchmark run on \(\mathcal{D}_N\),
    which creates the first reference run for a monitored model;
    \item a routine monitoring run on the frozen \(n=300\) panel;
    \item an escalation full-benchmark run after a panel signal and diagnostic review;
    \item a candidate-comparison run on \(\mathcal{D}_N\) for deployment ranking.
\end{enumerate}

The first recorded run for a monitored model is a full-benchmark baseline on \(\mathcal{D}_N\).
The panel run is the weekly warning step.
The full-benchmark run is the decision step.
The panel answers whether paired performance changed on a fixed sensitivity set.
The full benchmark answers which candidate performs better on the broader comparison set.

\section{Inference and submission}
\label{sec:batch-process}
Each dataset row is normalized to
\[
\{\texttt{custom\_id},\ \texttt{body},\ \texttt{campaign\_relevant}\}.
\]
Each normalized row contains a stable join key \texttt{custom\_id}, a provider
request payload \texttt{body} built from the fixed template
\mbox{\codepath{config/request_template.json}} and the item's multimodal input,
and the ground-truth label \texttt{campaign\_relevant} for scoring.
Repeated runs keep the dataset items, request template, campaign instruction,
output schema, and response parser fixed, which stabilizes both the request
payload and the interpretation of the returned JSON.

The merge is performed by\\
\mbox{\codepath{scripts/lib/load_dataset.py}}:
\[
\texttt{body}
=
\{\texttt{**request\_template},\ \texttt{"input"}:\texttt{item.input}\}.
\]
\texttt{item.input} is a Responses-style message array that carries the
campaign instruction, the user text, and any image inputs; the ground-truth
\texttt{campaign\_relevant} value stays beside \texttt{body} for scoring.

The template\\
\mbox{\codepath{config/request_template.json}}
stores provider responses (\texttt{store=true}) and requires a
\texttt{CampaignRelevanceMinimal} object with required fields
\texttt{campaign\_relevant} and \texttt{relevancy\_reasoning};
additional properties are forbidden. Scoring uses only
\texttt{campaign\_relevant}; \texttt{relevancy\_reasoning} is kept for audit.

\mbox{\codepath{scripts/run_eval.py}}
inserts the selected model and sends the canonical body to one of three
provider adapters: OpenAI, Gemini, or Claude. Table~\ref{tab:provider-adapters}
lists the JSONL envelope of each adapter.

\begin{table}[htbp]
\centering
\caption[Provider JSONL envelopes]{JSONL envelope fields written by each provider adapter.}
\label{tab:provider-adapters}
\begin{tabular}{@{}ll@{}}
\toprule
Provider & JSONL record fields \\
\midrule
OpenAI & \texttt{custom\_id}, \texttt{method}, \texttt{url}, \texttt{body} \\
Gemini & \texttt{key}, \texttt{request} \\
Claude & \texttt{custom\_id}, \texttt{params} \\
\bottomrule
\end{tabular}
\end{table}

\paragraph{OpenAI.}
Implemented in\\
\mbox{\codepath{scripts/batch_openai.py}}:
\begin{enumerate}
    \item POST to \texttt{/v1/responses};
    \item add the selected \texttt{model};
    \item keep \texttt{input}, image URLs, and \texttt{text.format};
    \item set low reasoning effort when the model supports it.
\end{enumerate}

\paragraph{Gemini.}
Implemented in\\
\mbox{\codepath{scripts/batch_gemini.py}}:
\begin{enumerate}
    \item map system text to \texttt{systemInstruction};
    \item map user parts to \texttt{contents};
    \item replace image URLs by Files API \texttt{fileData} URI/MIME pairs;
    \item map the schema to \texttt{generationConfig.responseSchema};
    \item set temperature zero and disable thinking when supported.
\end{enumerate}

\paragraph{Claude.}
Implemented in\\
\mbox{\codepath{scripts/batch_claude.py}}:
\begin{enumerate}
    \item sanitize \texttt{custom\_id} reversibly;
    \item map input to \texttt{system} and \texttt{messages}, keeping URL image sources;
    \item map the schema to \texttt{output\_config.format};
    \item set \texttt{max\_tokens=1024} and low effort when supported.
\end{enumerate}

Every invocation receives a UTC \texttt{run\_id}, and submission records that
identifier, the requested subset size, and each model's provider and batch
identifier in \texttt{data/batch\_ids.json}; failed submissions retain a null
batch identifier and an error message.

\section{Retrieval, completeness, and scoring}
\label{sec:metrics-dashboard}
\mbox{\codepath{scripts/poll_and_ingest.py}}
restores the manifest and then:
\begin{enumerate}
    \item polls each submitted batch;
    \item downloads each completed batch as a JSONL file in \texttt{data/results/};
    \item calls \texttt{ingest\_results(...)} from \mbox{\codepath{scripts/ingest.py}};
    \item reports failed, cancelled, expired, and timed-out jobs separately;
    \item lists missing result files in the retrieval summary.
\end{enumerate}
A missing result file leaves the corresponding model--run incomplete.
Reviewers check completeness before reading any paired panel result.

For downloaded rows,\\
\mbox{\codepath{scripts/ingest.py}}
does the following:
\begin{enumerate}
    \item joins each response to its label by \texttt{custom\_id};
    \item extracts the returned binary prediction and token usage;
    \item computes the token-derived inference cost when pricing is available;
    \item creates a Langfuse trace, span, and generation for the returned row;
    \item records \texttt{model}, \texttt{provider}, \texttt{custom\_id}, and \texttt{run\_id}
    in Langfuse metadata;
    \item writes Langfuse scores for \texttt{accuracy}, \texttt{error\_type}, and
    \texttt{cost\_usd} when those values are available.
\end{enumerate}
Rows without a matching label receive no \texttt{accuracy} or \texttt{error\_type} score.

An absent provider result leaves no scored row.
A returned row with a missing or invalid structured boolean is parsed as
\texttt{false}; that fallback keeps the row, so format failures stay visible
in retrieval summaries and trace inspection.

\subsection{Dashboard review interface}
The read-only Streamlit dashboard implemented in\\
\mbox{\codepath{streamlit_app/app.py}}
uses offline CSV snapshots written by\\
\mbox{\codepath{streamlit_app/export_langfuse_csv.py}}.
That export script fetches traces and scores from the Langfuse API and writes
\texttt{langfuse\_traces.csv} and \texttt{langfuse\_scores.csv}.
The live review app is available at\\
\url{https://llm-eval-dashboard.streamlit.app/}.
These snapshots drive three views:
\begin{enumerate}
    \item overview of accuracy traces by model and run;
    \item paired McNemar evidence;
    \item expected-cost ranking on common benchmark cases.
\end{enumerate}
Screenshots of those views are shown in Appendix~\ref{app:dashboard-views}
(Figure~\ref{fig:dashboard-canonical}).
An external email notification opens the review step after an alert.
The same evidence store then supports the follow-up checks and any later escalation.

The third view implements the expected-cost ranking of
Chapter~\ref{ch:cost-deployment-utility} on the common benchmark cases.
Every candidate is scored on the same labelled items.
For each candidate the dashboard displays
\begin{equation}
L_t(m)
=
c_t(m)
+
\frac{
C_{\mathrm{FP}}\,\mathrm{FP}_t(m)
+
C_{\mathrm{FN}}\,\mathrm{FN}_t(m)
}{n_t},
\label{eq:dashboard-expected-cost}
\end{equation}
which is Equation~\eqref{eq:expected-cost}.
The displayed terms are:
\begin{enumerate}
    \item \(c_t(m)\): API charge per case for candidate \(m\);
    \item \(\mathrm{FP}_t(m)\), \(\mathrm{FN}_t(m)\): false-positive and false-negative counts
    on the common benchmark cases;
    \item \(n_t\): number of those common cases;
    \item \(C_{\mathrm{FP}}\), \(C_{\mathrm{FN}}\): reviewer-chosen scenario penalties.
\end{enumerate}
For example, if \(C_{\mathrm{FP}}=1\), \(C_{\mathrm{FN}}=4\),
\(\mathrm{FP}_t(m)=3\), \(\mathrm{FN}_t(m)=5\), and \(n_t=500\),
then the penalty term is
\((1\cdot 3 + 4\cdot 5)/500 = 0.046\) cost units per case
before the API charge \(c_t(m)\) is added.
A reviewer can change the penalties, or the ratio \(C_{\mathrm{FN}}/C_{\mathrm{FP}}\),
and the ranking updates immediately.
The highlighted bar is the candidate with the lowest displayed expected cost
under the current settings.
The dashboard reports that ranking for review;
the engineer then recommends a deployment change.

\section{Run identity and stored artifacts}
\label{sec:artifacts-data-flow}
Here, a \emph{run} means one submission event covering one dataset subset and one or more models.
Its \texttt{run\_id} distinguishes results from different scheduled executions.
Within a run, one prediction is identified by
\[
(\texttt{run\_id},\ \texttt{provider},\ \texttt{model},\ \texttt{custom\_id}).
\]
The first three fields identify the execution and model;
\texttt{custom\_id} identifies the benchmark item and joins it to its baseline prediction and label.

The workflow persists five artifact classes:
\begin{enumerate}
    \item \textbf{Batch manifest} (\texttt{data/batch\_ids.json}):
    records \texttt{run\_id}, dataset choice, provider, model, and submitted batch identifiers;
    connects submission, retrieval, and audit of incomplete or failed jobs.
    \item \textbf{Raw provider outputs} (\texttt{data/results/}):
    keep item-level responses keyed by \texttt{custom\_id};
    support rescoring, parser review, and repeated export without new inference.
    \item \textbf{Langfuse traces}:
    store run metadata, model identity, benchmark item, and parsed prediction;
    provide the canonical item-level record for review and dashboard export.
    \item \textbf{Langfuse scores}:
    store correctness, TP/FP/TN/FN type, and token-derived cost;
    feed paired monitoring, benchmark comparison, and cost-aware ranking.
    \item \textbf{Dashboard snapshots}:
    present trajectories, paired evidence, and candidate comparisons;
    support human review, reporting, and deployment discussion.
\end{enumerate}

These records keep predictions from different executions separate and pair the same
benchmark item across runs.
Saved provider responses allow scoring and statistical analysis to be repeated without
calling the model again.
Stronger replay would also require immutable hashes for the dataset, request template,
prompt, parser, and model configuration.

For the fixed datasets used in this thesis, the persisted identifiers are:
\begin{enumerate}
    \item benchmark:\\
    \mbox{\texttt{campaign\_relevance\_02e1a68ccb0f}};
    \item monitoring panel:\\
    \mbox{\texttt{campaign\_relevance\_disagree\_subset\_9d488308aa46}}.
\end{enumerate}
Langfuse-backed traces, scores, and their export layer preserve these dataset keys,
so every reported value stays traceable to one fixed benchmark or panel definition.

The public code repository keeps the reproducibility inputs upstream of these records,
including the evaluation pipeline and the frozen Langfuse CSV snapshots\\
\mbox{\codepath{streamlit_app/langfuse_traces.csv}}
and\\
\mbox{\codepath{streamlit_app/langfuse_scores.csv}}.
Rendered figures, tables, and \LaTeX{} assets are part of this thesis source.

\section{Post-run decision logic}
\label{sec:decision-logic}
Figure~\ref{fig:run-decision-logic} shows the post-alert procedure.
After a panel alert, the reviewer follows these steps:
\begin{enumerate}
    \item check completeness, matched identifiers, missing pairs, and provider or parser failures;
    \item check whether the shift persists in the next run;
    \item check whether same-batch models moved in the same direction;
    \item if the episode remains sustained and actionable, run a full-benchmark evaluation of an
    alternative model and, optionally, of a revised prompt;
    \item compare predictive loss and API cost on \(\mathcal{D}_N\);
    \item recommend retaining the current setup, or recommend a model or prompt change under the
    declared acceptance rule.
\end{enumerate}
