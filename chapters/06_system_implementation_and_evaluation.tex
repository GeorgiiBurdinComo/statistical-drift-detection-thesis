\chapter{System Implementation}
\label{chap:system-architecture}

This chapter maps the statistical workflow to an auditable batch system. The implementation is intentionally narrower than a general MLOps platform: it preserves the fixed inputs needed for temporal comparison, records the identity and completeness of each run, and produces artifacts from which monitoring and ranking can be repeated.

\section{Pipeline boundary}
\label{sec:evaluation-pipeline-overview}
The implementation has five stages: load \(\mathcal{D}_n\) or \(\mathcal{D}_N\) from Langfuse; construct one canonical multimodal request; serialize it through a provider adapter; retrieve and score the asynchronous results; and export trace snapshots for analysis. Routine monitoring uses the frozen \(n=300\) panel. The full benchmark is reserved for baseline construction and explicit ranking or escalation. The changing model roster and token prices are configuration data in \texttt{config/models.yaml}, not part of the analytical design.

Figure~\ref{fig:ga-weekly-pipelines} shows the three scheduled workflows. Submission and retrieval are separate because provider batch APIs are asynchronous; the dashboard export begins only after retrieval and ingestion.

\section{Inference and submission}
\label{sec:batch-process}
Each dataset row is normalized to
\[
\{\texttt{custom\_id},\ \texttt{body},\ \texttt{campaign\_relevant}\}.
\]
The stable \texttt{custom\_id} is the join key across dates, providers, and ground truth. The request \texttt{body} combines the fixed template in \texttt{config/request\_template.json} with the item's multimodal input. Holding the template, prompt, dataset, output schema, and parser fixed prevents changes in request construction from being mistaken for changes in model output.

The merge performed by \texttt{load\_dataset.py} is explicit:
\[
\texttt{body}
=
\{\texttt{**request\_template},\ \texttt{"input"}:\texttt{item.input}\}.
\]
Here \texttt{item.input} is a Responses-style message array. A system item contains the campaign instruction; user content contains \texttt{input\_text} and zero or more \texttt{input\_image} parts with image URLs. The ground-truth \texttt{campaign\_relevant} value remains beside \texttt{body} and is not transmitted to the model.

The current template sets \texttt{store=true} and requests a strict JSON object named \texttt{CampaignRelevanceMinimal}. Its properties are \texttt{campaign\_relevant:boolean} and \texttt{relevancy\_reasoning:string}; both are required and \texttt{additionalProperties=false}. The reasoning string is therefore required by the current request schema, but it is auxiliary: ingestion stores it while all binary metrics use only \texttt{campaign\_relevant}.

\texttt{run\_eval.py} inserts the selected model and dispatches the canonical body to a provider adapter. Table~\ref{tab:provider-adapters} records the transformations implemented in the three adapters rather than treating them as interchangeable wire formats.

Every invocation receives a UTC \texttt{run\_id}. Submission writes \texttt{data/batch\_ids.json}, containing that identifier, the requested subset size, and each model's provider and batch identifier. A failed submission is retained in the manifest with a null batch identifier and an error message. Thus a run is identified by its manifest, not inferred later from timestamps.

\section{Retrieval, completeness, and scoring}
\label{sec:metrics-dashboard}
\texttt{poll\_and\_ingest.py} restores the manifest, polls each submitted batch, and writes completed JSONL files to \texttt{data/results/}. Failed, cancelled, expired, and timed-out jobs are reported separately. A missing result file is listed in the retrieval summary and is not replaced by synthetic predictions; the corresponding model--run is incomplete and must not be used as a complete panel observation. The retrieval code reports this state but does not enforce an \(n\)-row completeness gate in the dashboard, so completeness must be checked before a paired test is interpreted.

For downloaded rows, \texttt{ingest.py} joins the response to its label by \texttt{custom\_id}, records \texttt{model}, \texttt{provider}, and \texttt{run\_id} in trace metadata, and writes three downstream quantities: binary correctness, the TP/FP/TN/FN error type, and token-derived inference cost. Precision, recall, and F1 are then computed as defined in Section~\ref{sec:classification-metrics}. Results without a matching label receive no accuracy or error-type score.

The implementation distinguishes an absent provider result from a malformed returned result. Absence leaves no scored row. By contrast, the current parser maps a missing or invalid structured boolean in a returned row to \texttt{false}; this deterministic fallback avoids silently dropping the row but makes format failure observationally indistinguishable from a valid negative prediction. Schema-constrained responses reduce this risk, but completeness counts and provider error summaries remain necessary when interpreting a run.

The same scored outputs feed a read-only Streamlit reporting layer used with product stakeholders. Offline Langfuse score and trace snapshots drive three views: Overview (filterable metric trajectories by model and date), McNemar Test (paired alert evidence), and Expected Cost (deployment ranking under declared FP/FN penalties). Figures~\ref{fig:dashboard-overview}--\ref{fig:dashboard-cost} show the implemented tabs. The dashboard does not execute alert or deployment actions; those decisions remain outside the UI.

\section{Run identity and stored artifacts}
\label{sec:artifacts-data-flow}
Here, a \emph{run} means one submission event covering one dataset subset and one or more models. Its \texttt{run\_id} distinguishes results produced by different scheduled executions. Within a run, one prediction is identified by
\[
(\texttt{run\_id},\ \texttt{provider},\ \texttt{model},\ \texttt{custom\_id}).
\]
The first three fields identify the execution and model; \texttt{custom\_id} identifies the benchmark item and permits an exact join to its baseline prediction and label.

The persisted records have the following schemas (question marks denote optional fields and \texttt{|} alternatives):
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,columns=fullflexible]
batch_ids.json = {
  "run_id": string,
  "subset_size": integer,
  "batches": [{
    "model": string,
    "provider": string,
    "batch_id": string | null,
    "error"?: string,
    "claude_id_map"?: object
  }]
}

result JSONL row = {
  ("custom_id" | "key"): string,
  "response": provider_response
}

Langfuse trace = {
  "id": string,
  "timestamp": datetime,
  "metadata": {
    "run_id": string, "provider": string, "model": string,
    "custom_id": string, "batch_eval": boolean
  },
  "output": {"campaign_relevant": boolean}
}

Langfuse score = {
  "traceId": string,
  "name": string,
  ("value": number | "stringValue": string)
}
\end{lstlisting}
The manifest connects a local run to each provider batch. Each downloaded JSONL row retains the provider response and item identifier. Ingestion converts that row into a trace and attaches accuracy, error type, and cost as scores; \texttt{traceId} joins the score records back to the trace. The analysis export then selects the trace identity fields and score values into CSV snapshots.

These records serve two purposes. First, \texttt{run\_id} keeps predictions from different weekly executions separate, while \texttt{custom\_id} pairs the same benchmark item across runs. Second, the saved provider responses allow scoring and statistical analysis to be repeated without calling the model again. This reproduces the processing of existing outputs, not the original model inference. Repeating the inference exactly would additionally require immutable copies or hashes of the dataset, request template, prompt, parser, and model configuration; the current manifest records only the subset size and provider batch identifiers.

\section{Post-run decision logic}
\label{sec:decision-logic}
The implementation keeps monitoring and ranking as separate transitions (Figure~\ref{fig:run-decision-logic}). An eligible panel run is compared with the model's baseline on \(\mathcal{D}_n\). The alert rule combines paired statistical evidence with the operational magnitude floor. If it passes, three diagnostics determine whether escalation is justified. First, the run manifest, matched identifiers, missing pairs, provider errors, and malformed structured outputs are audited; this matters because the parser maps an invalid returned boolean to \texttt{false}. Second, the next scheduled observation is checked to distinguish persistence from a rebound. Third, models evaluated in the same batch are inspected for a shared failure pattern. These other models provide context, not formal controls for every model-specific mechanism. Only a credible, operationally actionable episode opens full-benchmark candidate comparison. The dashboard reports this evidence but does not execute a configuration change automatically.

Because provider weights are inaccessible, an observed behavioural change leaves two controllable candidate-generation actions: switch to another available model, or revise the hard prompt while retaining the model. The dotted branch in Figure~\ref{fig:run-decision-logic} denotes the second, optional action. Appendix~\ref{app:prompt-optimisation} describes automatic prompt optimisation and the exploratory GEPA runs. A revised prompt is not accepted because its optimisation score improved; it enters the same evaluation on \(\mathcal{D}_N\) and the same acceptance rule as a model-switch candidate.
