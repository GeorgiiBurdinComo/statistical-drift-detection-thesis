\chapter{System Implementation and Experimental Evaluation}
\label{chap:system-architecture}

This chapter describes the implemented monitoring system, the experimental setup, and the results obtained on the fixed monitoring subset in the observed time window.

\section{Overview}
\label{sec:evaluation-pipeline-overview}

The monitoring system has five main layers:
\begin{enumerate}
    \item a \textbf{dataset layer} in Langfuse, which stores the full benchmark and the frozen monitoring subset;
    \item a \textbf{normalization and orchestration layer}, centered on \texttt{run\_eval.py}, which loads examples and builds one canonical request format;
    \item a \textbf{provider adapter layer}, which converts that format into the native batch formats of OpenAI, Gemini, and Claude;
    \item a \textbf{retrieval and ingestion layer}, which downloads completed batch outputs, joins them with the ground truth, and writes traces and scores to Langfuse; and
    \item an \textbf{export and dashboard layer}, which creates committed CSV snapshots for routine inspection.
\end{enumerate}
Operationally, these layers are implemented by the three scheduled GitHub Actions workflows shown in Figure~\ref{fig:ga-weekly-pipelines}:
\begin{itemize}
    \item \texttt{weekly\_drift\_monitoring.yml} --- submits evaluation batches,
    \item \texttt{weekly\_retrieve.yml} --- polls for completion and ingests results,
    \item \texttt{sync-streamlit-dashboard.yml} --- exports and synchronizes dashboard metrics.
\end{itemize}

The system supports two run types:
\begin{itemize}
    \item \textbf{Benchmark run}: evaluates all monitored models on the full reference dataset (\(N=1199\)), costs about USD~90 per pass, and is used for baseline initialization and explicit escalation.
    \item \textbf{Monitoring run}: evaluates the same model roster on the frozen disagreement-based subset (\(n=300\)), costs about USD~20 per pass, and is executed weekly.
\end{itemize}
Routine automation runs only on the fixed 300-example panel; full-benchmark evaluation is outside the weekly cycle.

The monitored models and token prices used for cost accounting are defined in \texttt{config/models.yaml} and summarized in Table~\ref{tab:monitored-models}.

\section{Implemented Monitoring Pipeline}

The pipeline runs in three separate stages because provider batch APIs are asynchronous: submission and result retrieval cannot be done in the same job. Figure~\ref{fig:ga-weekly-pipelines} shows the weekly schedule.

\begin{figure}[H]
    \hspace*{-0.25\textwidth}
    \includegraphics[width=1.4\textwidth]{assets/fig-5-3-ga-pipeline.png}
    \caption{Scheduled GitHub Actions workflows for monitoring submission, retrieval, and dashboard synchronization.}
    \label{fig:ga-weekly-pipelines}
\end{figure}

The three workflows are:
\begin{itemize}
    \item \texttt{weekly\_drift\_monitoring.yml}, which submits batches via \texttt{run\_eval.py} (Friday 05:00 UTC);
    \item \texttt{weekly\_retrieve.yml}, which restores \texttt{data/batch\_ids.json}, runs \texttt{poll\_and\_ingest.py}, and ingests results into Langfuse (Monday 05:00 UTC);
    \item \texttt{sync-streamlit-dashboard.yml}, which exports CSV snapshots and mirrors the dashboard repository (Monday 07:00 UTC).
\end{itemize}

\subsection{Workflow~1: Submit Batches}
\label{sec:batch-process}

\textbf{Schedule.}

\texttt{weekly\_drift\_monitoring.yml} runs every Friday at 05:00 UTC.

\textbf{Data sources.}\label{sec:dataset-storage}

The implementation uses two Langfuse datasets:
\begin{itemize}
    \item the reference benchmark (\(N=1199\));
    \item the monitoring subset (\(n=300\)).
\end{itemize}
In regular operation, the weekly workflow submits only the frozen monitoring subset. The full benchmark is not part of the weekly cron loop and is used only for initialization or explicit escalation.

Langfuse is the single source of truth for benchmark rows and labels. Each row contains:
\begin{itemize}
    \item a stable \texttt{custom\_id}, reused throughout request construction, batch submission, result files, ingested traces, CSV exports, and statistical analysis;
    \item the campaign description;
    \item post text;
    \item transcription;
    \item hashtags;
    \item media references;
    \item frame references (where needed);
    \item the ground-truth boolean \texttt{campaign\_relevant} (JSON \texttt{true}/\texttt{false}).
\end{itemize}
Since the 300-example monitoring subset is selected once and then kept fixed, paired McNemar comparisons are not affected by changes in sample composition.

\textbf{Request normalization.}

Rows are normalized to the shared structure
\[
\{\texttt{custom\_id},\;\texttt{body},\;\texttt{campaign\_relevant}\}.
\]
The \texttt{body} uses an OpenAI-style Responses request object: a fixed template from \texttt{config/request\_template.json} is merged with the per-item multimodal \texttt{input} loaded from Langfuse. A local CSV path is also supported so that the frozen subset can be replayed without live Langfuse access. Because the same canonical representation is used in every routine monitoring run, temporal comparisons keep the task and prompt template fixed. Differences over time are therefore attributed to provider-side model changes rather than to changes in request construction.

\textbf{Orchestration.}

The orchestrator \texttt{run\_eval.py} does the following:
\begin{itemize}
    \item loads the selected evaluation subset (weekly default: the frozen \(n=300\) panel);
    \item ensures Gemini image uploads when any Gemini model is selected;
    \item dispatches each model to the corresponding \texttt{batch\_*.py} adapter.
\end{itemize}
Each adapter then:
\begin{itemize}
    \item serializes the canonical request body into the provider's native batch format;
    \item uploads the JSONL file;
    \item submits an asynchronous batch job.
\end{itemize}
After that, the orchestrator:
\begin{itemize}
    \item collects the returned batch identifiers into the run manifest \texttt{data/batch\_ids.json}, which stores \texttt{run\_id}, \texttt{subset\_size}, and the per-model batch identifiers;
    \item stores this manifest in the GitHub Actions cache so that the retrieval workflow can restore the submission state.
\end{itemize}

\textbf{Provider-specific batch adapters.}\label{sec:provider-adapters}

The prediction task is the same for all providers: each example must return a JSON boolean field \texttt{campaign\_relevant} (\texttt{true} or \texttt{false}) from the same multimodal input and under the same schema-constrained output format. The only differences are in the adapter layer required by each provider API. Table~\ref{tab:provider-adapters} shows the two comparable adapter aspects: response-shape enforcement and provider-specific preprocessing before submission.

\textbf{Identifier integrity across providers.}

The canonical \texttt{custom\_id} is the join key for the full pipeline. For Claude, submission requires a sanitized transport-level identifier, but the original benchmark identifier is kept in the canonical request representation and restored during result download. This ensures that every prediction can be matched back to the original benchmark row and ground-truth label.

\textbf{Gemini image preprocessing.}

Gemini batch lines require uploaded file URIs instead of remote HTTP image URLs. The helper \texttt{upload\_gemini\_images.py} downloads each distinct URL, uploads it via the Gemini Files API, and stores the URI, file name, and upload timestamp for each URL in \texttt{data/gemini\_image\_cache.json}. Entries older than the cache TTL are ignored when new batches are built, so stale file handles are not reused.

The transport-level differences are easiest to see in abbreviated examples:

Across all three providers, the output is constrained to the same minimal monitoring schema:
\[
\{\texttt{campaign\_relevant},\; \texttt{relevancy\_reasoning}\},
\]
with \texttt{campaign\_relevant} typed as a JSON \texttt{boolean} in the schema.

\textbf{Output.}

The submission workflow produces \texttt{data/batch\_ids.json} for the retrieval workflow and the per-model JSONL files under \texttt{batches/} that have been submitted to the provider batch APIs.

\subsection{Workflow~2: Retrieve and Ingest}
\label{sec:metrics-dashboard}

\textbf{Schedule.}

\texttt{weekly\_retrieve.yml} runs every Monday at 05:00 UTC.

\textbf{Polling and download.}

The script \texttt{poll\_and\_ingest.py} restores \texttt{data/batch\_ids.json} from the Actions cache, polls each provider batch API until all jobs complete, and downloads the resulting JSONL outputs into \texttt{data/results/}.

\textbf{Ingestion.}

For each output line, the ingestion script \texttt{ingest.py} performs five steps:
\begin{enumerate}
    \item normalize the provider-specific response;
    \item extract the boolean \texttt{campaign\_relevant} and join it to the ground truth via \texttt{custom\_id};
    \item compute token usage from the provider-specific usage fields;
    \item convert token usage into USD cost via \texttt{config/models.yaml};
    \item write the resulting Langfuse trace together with derived scores and metadata.
\end{enumerate}

\textbf{Trace-level scores.}

Three trace-level scores are used later:
\begin{itemize}
    \item \texttt{accuracy}: a Langfuse numeric score with value \(1.0\) or \(0.0\), depending on whether the predicted boolean \texttt{campaign\_relevant} matches the ground truth;
    \item \texttt{error\_type}, which distinguishes true positives, false positives, true negatives, and false negatives;
    \item \texttt{cost\_usd}, which gives the realized cost of the request in USD.
\end{itemize}
From \texttt{error\_type}, precision, recall, and F1 are computed per run on \(\mathcal{D}_n\) as in Section~\ref{sec:classification-metrics}. The same trace store is therefore used for both paired drift tests and later model comparison.

\textbf{Output.}

After ingestion, Langfuse contains one trace per post per model, with the normalized response, provider and model identifiers, token usage, monetary cost, and derived scores. In this system, Langfuse acts both as the persistent registry of evaluation instances and as the historical log of model behaviour over time.

\subsection{Workflow~3: Dashboard Sync}

\textbf{Schedule.}

\texttt{sync-streamlit-dashboard.yml} runs every Monday at 07:00 UTC and on pushes to \texttt{main} that modify \texttt{streamlit\_app/}.

\textbf{CSV export.}

The script \texttt{export\_langfuse\_csv.py} paginates the Langfuse public API for traces and scores over a configured time window, flattens nested fields, keeps the columns used by the dashboard, and writes \texttt{streamlit\_app/langfuse\_traces.csv} and \texttt{langfuse\_scores.csv}. These files are committed to the main evaluation repository \texttt{gocomo/llm-batch-eval}.

\textbf{Repository mirror.}

The same workflow mirrors the full \texttt{streamlit\_app/} tree to the private dashboard repository \texttt{GeorgiiBurdinComo/llm-eval-dashboard}, from which the hosted Streamlit application is served. This keeps the dashboard reproducible and avoids storing long-lived Langfuse credentials in the hosted application.

\textbf{Dashboard.}

The dashboard has three main tabs:
\begin{itemize}
    \item \textbf{Overview}, which shows per-model accuracy over time together with aggregated cost summaries from \texttt{cost\_usd};
    \item \textbf{McNemar}, which reports paired contingency tables and exact \(p\)-values for selected run pairs;
    \item \textbf{Utility function}, which combines accuracy and cost through the expected-cost formulation \(E_t[\mathcal{C}](m)\) from Chapter~\ref{ch:cost-deployment-utility}.
\end{itemize}
In the utility tab, the trade-off control is parameterized as \(R=C_{\mathrm{FP}}/C_{\mathrm{FN}}\), so one false positive is treated as costly as \(R\) false negatives. The exported CSVs are also used in notebooks for additional inspection.

\section{Experimental Setup}
\label{sec:experimental-design}

The experiments use the full benchmark \(\mathcal{D}_N\) (\(N=1199\)) and the frozen subset \(\mathcal{D}_n\) (\(n=300\)) from Chapter~\ref{ch:data}. The discordant counts are \((b,c)=(10,10)\), so gains and losses balance exactly and there is no directional change.

For \texttt{gpt-4.1-nano}, the corresponding comparison in Table~\ref{tab:mcnemar_gpt41nano} gives \((b,c)=(22,26)\): 48 instances change status, with 22 regressions and 26 recoveries. The one-sided McNemar test does not reach \(\alpha=0.05\). Thus, despite noticeable churn, the net direction is not degradation under the alert rule from Chapter~\ref{ch:drift}.

These two examples show two different situations on the fixed panel: balanced movement with no directional evidence (\texttt{gpt-4.1-mini}) and high-churn but non-degrading movement (\texttt{gpt-4.1-nano}). In both cases, the correct operational response is continued monitoring together with preparation of fallback comparisons on the metric and cost panel.

\subsection{Candidate Comparison for Corrective Action}
\label{sec:cost-aware-comparison}

If drift is suspected, the next step is to compare alternative models. For each monitored run, the system records accuracy, precision, recall, F1, and mean cost per request. These quantities are first inspected on the fixed subset \(\mathcal{D}_n\). However, since \(\mathcal{D}_n\) is disagreement-based and not representative of the full benchmark, final deployment ranking by expected cost is computed on the full dataset \(\mathcal{D}_N\). In the implemented workflow, this full-benchmark comparison is used only after escalation, not in the routine weekly loop.

\section{Limitations}
\label{sec:error-analysis}


\begin{itemize}
    \item \(\mathcal{D}_n\) is disagreement-enriched and is therefore designed for sensitivity to instability, not for unbiased estimation of \(\mathcal{D}_N\) accuracy.
    \item Provider state is unobserved; drift is inferred only from output changes on the fixed panel.
    \item Cost depends on provider pricing and tokenization, so monetary comparisons may change even when the confusion structure stays the same.
    \item This chapter documents the implemented monitoring, escalation, and comparison pipeline, but not a full observed recovery episode after a verified alert.
\end{itemize}

This chapter presented the implemented monitoring architecture, the frozen-subset baseline, longitudinal paired evidence, and the corrective-action comparison panel. Evidence from an actual degradation-and-recovery episode is deferred to Chapter~\ref{chap:degradation-case-study}.
