\chapter{System Implementation}
\label{chap:system-architecture}

This chapter describes the batch system that runs the evaluation workflow. The implementation stores item-level outputs, scores, and run identifiers so completed runs can be rescored, paired, and audited without calling a model again. External providers return the model outputs. Local code fixes the datasets, builds requests, scores outputs, and exports the review views.

\section{System flow}
\label{sec:evaluation-pipeline-overview}
The system has five parts:
\begin{enumerate}
    \item fixed labelled datasets in Langfuse;
    \item request normalization and orchestration;
    \item provider-specific batch adapters;
    \item retrieval, ingestion, and scoring;
    \item a read-only dashboard for review.
\end{enumerate}
In this system, Langfuse serves as the persistent evaluation store. It holds the two fixed labelled datasets used in the thesis: the full 1199-item benchmark \texttt{campaign\_relevance\_02e1a68ccb0f} and the fixed 300-item monitoring panel \texttt{campaign\_relevance\_disagree\_subset\_9d488308aa46}. Each dataset item stores the multimodal input, the expected binary label \texttt{campaign\_relevant}, and stable metadata such as \texttt{custom\_id}. After each run, Langfuse also stores traces and scores for the returned outputs.
\reproanchor{The frozen benchmark definition is public in \codepath{prompt_optimization/splits/train.json}, \codepath{prompt_optimization/splits/val.json}, \codepath{prompt_optimization/splits/test.json}, and \codepath{prompt_optimization/splits/split_manifest.json}. The fixed 300-item monitoring panel is public in \codepath{notebooks/canonical_evidence_export/panel_ids.txt}; the scored run snapshots used throughout the thesis are \codepath{streamlit_app/langfuse_traces.csv} and \codepath{streamlit_app/langfuse_scores.csv}. Dataset sync logic lives in \codepath{scripts/sync_dataset.py}.}

The public code repository for this pipeline is \url{https://github.com/GeorgiiBurdinComo/llm-batch-eval}. It contains the batch-evaluation code, workflow automation, prompt-optimisation code, and the frozen reproducibility inputs used to regenerate the published evidence. The public manuscript repository is \url{https://github.com/GeorgiiBurdinComo/statistical-drift-detection-thesis}; it contains the thesis source and the publication-ready assets consumed by the \LaTeX{} build.

These parts support three run types:
\begin{itemize}
    \item a routine monitoring run evaluates the frozen \(n=300\) panel;
    \item a full-benchmark run evaluates \(\mathcal{D}_N\) during baseline construction or candidate comparison;
    \item an escalation run is a full-benchmark run requested after a panel signal and diagnostic review.
\end{itemize}

The panel run is the weekly warning step because it is cheap enough to repeat. The full benchmark run is the decision step because candidate ranking requires the broader labelled set. The panel answers whether paired performance changed on a fixed sensitivity set. The full benchmark answers which candidate performs better on the broader comparison set.

Figure~\ref{fig:ga-weekly-pipelines} shows the three scheduled workflows. Submission and retrieval run as separate jobs because provider batch APIs are asynchronous. The dashboard export starts only after retrieval and ingestion finish.

\section{Inference and submission}
\label{sec:batch-process}
Each dataset row is normalized to
\[
\{\texttt{custom\_id},\ \texttt{body},\ \texttt{campaign\_relevant}\}.
\]
The normalized row has three fields:
\begin{description}
    \item[\texttt{custom\_id}] stable join key across dates, providers, and ground truth;
    \item[\texttt{body}] request body obtained by combining the fixed template in \texttt{config/request\_template.json} with the item's multimodal input;
    \item[\texttt{campaign\_relevant}] local ground-truth label used during scoring.
\end{description}
Holding the template, prompt, dataset, output schema, and parser fixed keeps request construction stable across repeated runs.

The merge performed by \texttt{load\_dataset.py} is explicit:
\[
\texttt{body}
=
\{\texttt{**request\_template},\ \texttt{"input"}:\texttt{item.input}\}.
\]
Here \texttt{item.input} is a Responses-style message array. A system item contains the campaign instruction; user content contains \texttt{input\_text} and zero or more \texttt{input\_image} parts with image URLs. The ground-truth \texttt{campaign\_relevant} value remains beside \texttt{body} and stays local to scoring.

The current template sets \texttt{store=true} and requests a strict JSON object named \texttt{CampaignRelevanceMinimal}. Its properties are \texttt{campaign\_relevant:boolean} and \texttt{relevancy\_reasoning:string}; both are required and \texttt{additionalProperties=false}. The reasoning string is stored for audit, while all binary metrics use only \texttt{campaign\_relevant}.

\texttt{run\_eval.py} inserts the selected model and dispatches the canonical body to a provider adapter. Table~\ref{tab:provider-adapters} records the transformations implemented in the three adapters.

\begin{table}[htbp]
\centering
\scriptsize
\caption[Exact provider batch mapping]{Provider-specific JSONL envelopes and transformations applied to the canonical request body.}
\label{tab:provider-adapters}
\begin{tabularx}{\linewidth}{lYY}
\toprule
Provider & One JSONL record & Implemented request transformation \\
\midrule
OpenAI &
\texttt{\{custom\_id, method, url, body\}} &
\texttt{POST /v1/responses}; add \texttt{model}; preserve canonical \texttt{input}, image URLs, and \texttt{text.format}; use low reasoning effort for supported models. \\
Gemini &

Claude &
\texttt{\{custom\_id, params\}} &
Sanitize the ID reversibly; map input to \texttt{system} and \texttt{messages}, retaining URL image sources; map the schema to \texttt{output\_config.format}; set \texttt{max\_tokens=1024} and low effort where supported. \\
\bottomrule
\end{tabularx}
\end{table}

Every invocation receives a UTC \texttt{run\_id}. Submission writes \texttt{data/batch\_ids.json}, containing that identifier, the requested subset size, and each model's provider and batch identifier. A failed submission is retained in the manifest with a null batch identifier and an error message. Thus a run is identified by its manifest.

\section{Retrieval, completeness, and scoring}
\label{sec:metrics-dashboard}
\texttt{poll\_and\_ingest.py} restores the manifest, polls each submitted batch, and writes completed JSONL files to \texttt{data/results/}. Failed, cancelled, expired, and timed-out jobs are reported separately. A missing result file is listed in the retrieval summary and leaves the corresponding model--run incomplete. Reviewers check completeness before reading any paired panel result.

For downloaded rows, \texttt{ingest.py} joins the response to its label by \texttt{custom\_id}, records \texttt{model}, \texttt{provider}, and \texttt{run\_id} in trace metadata, and writes three downstream quantities: binary correctness, the TP/FP/TN/FN error type, and token-derived inference cost. Precision, recall, and F1 are then computed as defined in Section~\ref{sec:classification-metrics}. Results without a matching label receive no accuracy or error-type score.

The implementation distinguishes an absent provider result from a malformed returned result. Absence leaves no scored row. By contrast, the current parser maps a missing or invalid structured boolean in a returned row to \texttt{false}; this deterministic fallback keeps the row, so format failures remain visible through retrieval summaries and trace inspection.

The same scored outputs are exported to a read-only Streamlit dashboard used in stakeholder review. Offline Langfuse score and trace snapshots drive:
\begin{itemize}
    \item an overview of accuracy traces by model and run;
    \item paired McNemar evidence;
    \item expected-cost ranking on common benchmark cases.
\end{itemize}
An external email notification opens the review step after an alert. The same evidence store then supports the follow-up checks and any later escalation.

The third view implements the expected-cost ranking of Chapter~\ref{ch:cost-deployment-utility} on the common benchmark cases. It uses the common cases so every candidate is scored on the same labelled items. For each candidate it displays
\begin{equation}
L_t(m)
=
c_t(m)
+
\frac{
C_{\mathrm{FP}}\,\mathrm{FP}_t(m)
+
C_{\mathrm{FN}}\,\mathrm{FN}_t(m)
}{n_t},
\label{eq:dashboard-expected-cost}
\end{equation}
which is Equation~\eqref{eq:expected-cost}. Here \(c_t(m)\) is the API charge per case for candidate \(m\), \(\mathrm{FP}_t(m)\) and \(\mathrm{FN}_t(m)\) are its false-positive and false-negative counts on the common benchmark cases, and \(n_t\) is the number of those common cases. The penalties \(C_{\mathrm{FP}}\) and \(C_{\mathrm{FN}}\) set the review scenario. For example, if \(C_{\mathrm{FP}}=1\), \(C_{\mathrm{FN}}=4\), \(\mathrm{FP}_t(m)=3\), \(\mathrm{FN}_t(m)=5\), and \(n_t=500\), then the penalty term is \((1\cdot 3 + 4\cdot 5)/500 = 0.046\) cost units per case before the API charge \(c_t(m)\) is added. A reviewer can change the penalties, or the ratio \(C_{\mathrm{FN}}/C_{\mathrm{FP}}\), and the ranking updates immediately. The highlighted bar is the candidate with the lowest displayed expected cost under the current settings. The dashboard reports that ranking for review, after which the engineer can recommend a deployment change.

\section{Run identity and stored artifacts}
\label{sec:artifacts-data-flow}
Here, a \emph{run} means one submission event covering one dataset subset and one or more models. Its \texttt{run\_id} distinguishes results produced by different scheduled executions. Within a run, one prediction is identified by
\[
(\texttt{run\_id},\ \texttt{provider},\ \texttt{model},\ \texttt{custom\_id}).
\]
The first three fields identify the execution and model; \texttt{custom\_id} identifies the benchmark item and permits an exact join to its baseline prediction and label.

Table~\ref{tab:stored-artifacts} summarizes the main persisted artifacts and their roles in the workflow.

\begin{table}[htbp]
\centering
\small
\caption[Core persisted artifacts]{Core persisted artifacts used to connect asynchronous inference, rescoring, and review.}
\label{tab:stored-artifacts}
\begin{tabularx}{\linewidth}{lYY}
\toprule
Artifact & Purpose & Downstream use \\
\midrule
Batch manifest & Records \texttt{run\_id}, dataset choice, provider, model, and submitted batch identifiers. & Connects submission, retrieval, and audit of incomplete or failed jobs. \\
Raw provider outputs & Retain item-level responses keyed by \texttt{custom\_id}. & Support rescoring, parser review, and repeated export without new inference. \\
Langfuse traces & Store run metadata, model identity, benchmark item, and parsed prediction. & Provide the canonical item-level record for review and dashboard export. \\
Langfuse scores & Store correctness, TP/FP/TN/FN type, and token-derived cost. & Feed paired monitoring, benchmark comparison, and cost-aware ranking. \\
Dashboard snapshots and exports & Present trajectories, paired evidence, and candidate comparisons. & Support human review, reporting, and deployment discussion. \\
\bottomrule
\end{tabularx}
\end{table}

These records keep predictions from different executions separate and pair the same benchmark item across runs. Saved provider responses allow scoring and statistical analysis to be repeated without calling the model again. Stronger replay guarantees would additionally require immutable hashes for the dataset, request template, prompt, parser, and model configuration.

For the fixed datasets used in this thesis, the persisted benchmark identifier is \texttt{campaign\_relevance\_02e1a68ccb0f} and the persisted monitoring-panel identifier is \texttt{campaign\_relevance\_disagree\_subset\_9d488308aa46}. Langfuse-backed traces, scores, and their export layer preserve these dataset keys so every reported value remains traceable to one fixed benchmark or panel definition.

The public code repository keeps the reproducibility inputs that sit upstream of these stored records, including the evaluation pipeline, the frozen Langfuse CSV snapshots, and the canonical evidence export. The public manuscript repository keeps the rendered figures, tables, and \LaTeX{} assets cited in this thesis; exact prompt text is intentionally withheld from the public branch.
\reproanchor{The main code paths behind this storage layer are \codepath{scripts/run_eval.py}, \codepath{scripts/poll_and_ingest.py}, \codepath{scripts/ingest.py}, and \codepath{streamlit_app/export_langfuse_csv.py}. The frozen upstream manifests and hashes are published in \codepath{notebooks/canonical_evidence_export/input_manifest.json} and \codepath{notebooks/canonical_evidence_export/artifact_manifest.csv}.}

\section{Post-run decision logic}
\label{sec:decision-logic}
Figure~\ref{fig:run-decision-logic} shows the post-alert procedure. A panel alert first triggers a check of completeness, matched identifiers, missing pairs, and provider or parser failures. The reviewer then checks whether the shift persists in the next run and whether same-batch models moved in the same direction. If the episode remains sustained and actionable, the next step is a full-benchmark evaluation of an alternative model and, optionally, of a revised prompt.
