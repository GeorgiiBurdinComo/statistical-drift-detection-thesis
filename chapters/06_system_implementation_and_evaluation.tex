\chapter{System Implementation and Experimental Evaluation}
\label{chap:system-architecture}

The chapter describes the implemented monitoring system, the experimental setup, and the empirical results obtained on the fixed monitoring subset within the recorded time window. It focuses on operationalization rather than re-deriving the methodology: McNemar's test, evaluation metrics, and the manual selection procedure are defined in Chapter~\ref{ch:drift}, the expected-cost utility in Chapter~\ref{ch:cost-deployment-utility}, and prompt optimisation is discussed in Chapter~\ref{chap:prompt-optimisation}. Transient degradation behaviour is analysed separately in Chapter~\ref{chap:degradation-case-study}.

\section{Overview}
\label{sec:evaluation-pipeline-overview}

The monitoring system is implemented as a set of Python scripts orchestrated by three scheduled GitHub Actions workflows (Figure~\ref{fig:ga-weekly-pipelines}). Each workflow handles one stage of the evaluation cycle: submitting batch jobs to provider APIs (Friday), retrieving and ingesting results into Langfuse (Monday morning), and exporting CSV snapshots for the hosted Streamlit dashboard (Monday afternoon). Table~\ref{tab:artifact-inventory} in Section~\ref{sec:artifacts-data-flow} summarizes artifacts and handoffs across these stages.

The architecture supports two run types. A benchmark run evaluates all models on the full \(N=1199\) reference dataset (approximately USD~90 per pass) and is used once to construct the monitoring subset. A monitoring run evaluates models on the frozen \(n=300\) disagreement-based subset (approximately USD~20 per pass) and runs weekly to produce the longitudinal evidence analysed in the evaluation section.

The concrete set of monitored models and token prices used for cost accounting is defined in \texttt{config/models.yaml} and summarized in Table~\ref{tab:monitored-models}.

The pipeline runs in three stages, each triggered by a separate GitHub Actions workflow. Submission, retrieval, and dashboard synchronization are decoupled because provider batch APIs are asynchronous: results are not available immediately after submission.

\subsection{Workflow~1: Submit Batches}
\label{sec:batch-process}

\paragraph{Schedule.} \texttt{weekly\_drift\_monitoring.yml} runs every Friday at 05:00 UTC.

\paragraph{Data sources.}
\label{sec:dataset-storage}
The implementation uses two Langfuse datasets:
\begin{itemize}
    \item Reference benchmark (\(N=1199\))
    \item Monitoring subset (\(n=300\))
\end{itemize}

Langfuse acts as the single source of truth. Each row carries a stable \texttt{custom\_id} reused end-to-end across batch submission, result files, ingested traces, CSV exports, and statistical analyses. Each row includes the campaign description, post text, transcription, hashtags, media references, frame references where applicable, and the binary ground-truth label \texttt{campaign\_relevant}. The 300-example monitoring dataset is selected once from the full benchmark and then held fixed, so paired McNemar comparisons are not confounded by changes in sample composition.

\paragraph{Request normalization.}
Rows are normalized to a shared structure \texttt{\{custom\_id, body, campaign\_relevant\}}. The \texttt{body} follows an OpenAI-style Responses request object: a template from \texttt{config/request\_template.json} is merged with per-item multimodal \texttt{input} when loading from Langfuse. A local CSV path is also supported so the frozen subset can be replayed without live Langfuse access. The same representation is passed to all provider adapters, so only transport and provider-specific constraints differ downstream.

\paragraph{Orchestration.}
The orchestrator \texttt{run\_eval.py} loads the eval subset, optionally ensures Gemini image uploads when any Gemini model is selected, and dispatches each model to the corresponding \texttt{batch\_*.py} adapter. Each adapter serializes the canonical request body into the provider's native batch format, uploads the JSONL file, and submits an asynchronous batch job. The orchestrator collects the returned batch identifiers into a run manifest \texttt{data/batch\_ids.json} (containing \texttt{run\_id}, \texttt{subset\_size}, and per-model batch identifiers), which is saved to the GitHub Actions cache so the retrieve workflow can restore it.

\paragraph{Provider-specific batch adapters.}
\label{sec:provider-adapters}
The inference task is identical across providers: classify each example as campaign-relevant (binary \texttt{campaign\_relevant}) using the same multimodal input and the same JSON-schema-constrained output shape. What differs is only the adapter layer required by each provider API. Table~\ref{tab:provider-adapters} shows exactly what is mapped in that layer and why: batch wire format, response-shape enforcement, and provider-only preprocessing that must happen before submission. This comparison is transport-level only; task semantics and evaluation criteria remain unchanged.

\paragraph{Gemini image preprocessing.}
Gemini batch lines require uploaded file URIs instead of remote HTTP image URLs. The helper \texttt{upload\_gemini\_images.py} downloads each distinct URL, uploads via the Gemini Files API, and records URI, file name, and upload timestamp per URL in \texttt{data/gemini\_image\_cache.json}. Entries older than the TTL are ignored when building batches so stale file handles are not reused.

\[
\{\texttt{campaign\_relevant},\; \texttt{relevancy\_reasoning}\}.

\paragraph{Output.} The workflow produces \texttt{data/batch\_ids.json} (cached for the retrieve workflow) and per-model JSONL files under \texttt{batches/} that have been submitted to the provider batch APIs.

\subsection{Workflow~2: Retrieve and Ingest}
\label{sec:metrics-dashboard}

\paragraph{Schedule.} \texttt{weekly\_retrieve.yml} runs every Monday at 05:00 UTC.

\paragraph{Polling and download.}
The script \texttt{poll\_and\_ingest.py} restores \texttt{data/batch\_ids.json} from the Actions cache, polls each provider's batch API until all jobs complete, and downloads the result JSONL files into \texttt{data/results/}.

\paragraph{Ingestion.}
For each output line, the ingestion script \texttt{ingest.py} performs five steps:
\begin{enumerate}
    \item normalize the provider-specific response;
    \item extract \texttt{campaign\_relevant} and join it to the ground truth via \texttt{custom\_id};
    \item compute token usage from the provider-specific usage fields;
    \item convert token usage into USD cost via \texttt{config/models.yaml};
    \item write the resulting Langfuse trace together with derived scores and metadata.
\end{enumerate}

The full batch-API price table for all monitored models is provided in Appendix~\ref{app:batch-pricing-table} as Table~\ref{tab:batch-pricing-examples}.

\paragraph{Trace-level scores.}
Three scores are central for the later evaluation:
\begin{itemize}
    \item \texttt{accuracy} \(\in \{0,1\}\), indicating per-example correctness;
    \item \texttt{error\_type}, distinguishing true positives, false positives, true negatives, and false negatives;
    \item \texttt{cost\_usd}, giving the realized dollar cost of the request.
\end{itemize}

From \texttt{error\_type}, precision, recall, and F1 are computed per run on $\mathcal{D}_n$ as in Section~\ref{sec:classification-metrics}. The same traces feed drift tests and corrective-action comparisons.

\paragraph{Output.} Langfuse now holds one trace per example per model, with scores attached. Each trace stores the normalized response, provider and model identifiers, token usage, monetary cost, and derived scores; Langfuse therefore serves both as the registry of evaluation instances and as the persistent log of model behaviour over time.

\subsection{Workflow~3: Dashboard Sync}

\paragraph{Schedule.} \texttt{sync-streamlit-dashboard.yml} runs every Monday at 07:00 UTC and on pushes to \texttt{main} that change \texttt{streamlit\_app/}.

\paragraph{CSV export.}
The script \texttt{export\_langfuse\_csv.py} paginates the Langfuse public API for traces and scores over a configured time window, flattens nested fields, retains columns used by the app, and writes \texttt{streamlit\_app/langfuse\_traces.csv} and \texttt{langfuse\_scores.csv}. Those files are committed to the main evaluation repository \texttt{gocomo/llm-batch-eval}.

\paragraph{Repository mirror.}
The same workflow mirrors the full \texttt{streamlit\_app/} tree to the private dashboard repository \texttt{GeorgiiBurdinComo/llm-eval-dashboard}, from which the hosted Streamlit application is served. This keeps analytics reproducible and avoids embedding long-lived Langfuse credentials in the hosted app.

\paragraph{Dashboard.}
The dashboard exposes three main tabs. The overview tab shows per-model accuracy over time together with aggregated cost summaries from \texttt{cost\_usd}; the McNemar tab reports paired contingency tables and exact p-values for selected run pairs; and the utility-function tab combines accuracy and cost through the expected-cost formulation $E_t[\mathcal{C}](m)$ (Chapter~\ref{ch:cost-deployment-utility}) to support deployment trade-off analysis. In that utility tab, the trade-off control is parameterized as $R=C_{\mathrm{FP}}/C_{\mathrm{FN}}$, i.e.\ one false positive is treated as costly as $R$ false negatives. Exported CSVs also feed notebooks for inspection beyond the dashboard.

\label{sec:experimental-design}

The model roster is \texttt{config/models.yaml} (Table~\ref{tab:monitored-models}). Each run yields one trace per example and a paired correctness vector for McNemar comparisons (Section~\ref{sec:mcnemar-section}).

In the monitor--detect--act logic, this state is treated as watch-and-compare: keep observing drift evidence while preparing fallback comparisons using the metric/cost panel.

\subsection{Candidate Comparison for Corrective Action}
\label{sec:cost-aware-comparison}

This result block asks how a monitoring system should support choice among candidate corrective actions once predictive quality and cost are both visible. Each monitored run yields empirical accuracy, precision, recall, and F1 on the fixed subset together with mean per-request cost (Chapter~3). However, because the monitoring subset is disagreement-enriched and not distribution-representative, the expected-cost ranking used for deployment decisions is computed on the full benchmark $\mathcal{D}_N$. Operators compare candidates manually: some campaigns tolerate more false positives than others, so no single ranking rule is imposed in the experiments reported here.

\section{Limitations}
\label{sec:error-analysis}

False positives often track superficial lexical cues (brands, slogans, hashtags); false negatives often reflect implicit or multimodal relevance. The former are local to text rules; the latter are harder to fix by prompt alone.

\begin{itemize}
    \item $\mathcal{D}_n$ is disagreement-enriched: it monitors instability, not unbiased $\mathcal{D}_N$ accuracy.
    \item Provider state is unobserved; drift is inferred from outputs on $\mathcal{D}_n$ only.
    \item Cost varies with pricing and tokenisation even when labels are stable.
    \item GEPA is constrained to verified drift and re-evaluation on $\mathcal{D}_n$ to limit overfitting to hard cases.
\end{itemize}

The chapter shows the implemented monitoring pipeline, the frozen-subset baseline, longitudinal paired evidence, and a corrective-action comparison panel. It does not include an observed alert-to-deployment recovery episode; such evidence is discussed separately in Chapter~\ref{chap:degradation-case-study} when available.
