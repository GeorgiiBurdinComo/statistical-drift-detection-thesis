\chapter{Exploratory Automatic Prompt Optimisation}
\label{app:prompt-optimisation}

\section{Purpose and protocol}

In this thesis, automatic prompt optimisation is an attempted repair of the same campaign-relevance classifier studied in the main chapters. For each post, the model still receives the same campaign definition, post text, and visual content and must still return the same binary label \texttt{campaign\_relevant} \(\in \{0,1\}\). What changes is only the client-controlled instruction prompt that tells the model how to interpret those inputs and where to place the decision boundary between relevant and non-relevant posts.

This distinction matters for the drift framework. Passive monitoring keeps the full request contract fixed and asks whether the provider-side behaviour changed over time. If a closed provider model starts behaving differently, its internal cause cannot be inspected or repaired directly by the user. In that situation, one plausible question is whether a small change in the prompt can restore the earlier decision behaviour without switching to another model. Prompt optimisation is different from monitoring because it is an intentional intervention. Once the prompt is rewritten, the system is no longer the original monitored configuration but a new model--prompt candidate that must be evaluated again under the same benchmark protocol before any deployment decision.

Operationally, APO treats prompt repair as a black-box search problem. A human-written seed prompt is run on labelled classification examples, the error pattern is converted into feedback, and the optimiser proposes revised prompts that may express the relevance rule more clearly or more robustly. The model weights, provider endpoint, output schema, parser, and labels remain fixed during that search; only the prompt text is edited.

A valid APO experiment also needs separation between search and final evaluation. The optimiser may inspect mistakes on an adaptation set and use them to revise the prompt. A separate validation set is then used to select a candidate. A sealed test set is touched only after selection. If test results are inspected while deciding whether to continue, repeat, or reinterpret the search, the evidence becomes exploratory rather than confirmatory. That is the status of the runs reported here.

\section{Exploratory GEPA runs}

The exploratory trial used GEPA (Genetic--Pareto Evolutionary Prompt Optimisation)~\cite{agrawal2025gepa}. In the present setting, a candidate is simply one version of the campaign-relevance instruction prompt. The seed prompt already specifies the task and required boolean output; GEPA does not invent a new task, but rewrites that instruction after observing where the current prompt misclassifies labelled posts.
The public code repository \url{https://github.com/GeorgiiBurdinComo/llm-batch-eval} stores the frozen split manifest under \texttt{prompt\_optimization/splits/} and the run-level GEPA summaries under \texttt{prompt\_optimization/runs/}. The public manuscript repository \url{https://github.com/GeorgiiBurdinComo/statistical-drift-detection-thesis} stores the rendered appendix assets cited here. Exact prompt text is intentionally withheld from both public branches.

Concretely, GEPA evaluates a parent prompt on a minibatch of benchmark items, identifies which posts were classified incorrectly, and turns those failures into textual feedback for a reflection model. The offspring prompt may then sharpen the relevance criterion, reduce over-triggering on weak brand cues, or better state when merchandise-only or context-poor posts should stay negative. Each offspring is therefore another candidate binary classifier for the same task, not a free-form prompt variant judged subjectively.

GEPA keeps a population of prompts that perform well on different validation items instead of immediately collapsing the search to one average-best incumbent. This is useful for campaign-relevance classification because the hard cases near the effective decision boundary are heterogeneous: one edit may recover visually implied positives but introduce new false positives on loosely related brand mentions, while another edit does the opposite. Population retention preserves such alternatives until the validation rule selects one.

Two runs used the same \(719/239/241\) train/validation/test split. Both validation-selected prompts improved validation accuracy, but their descriptive test outcomes differed:

The two outcomes move in opposite directions. This shows two things at once. First, even with a closed API model, automated prompt search can sometimes recover noticeably better classification behaviour on the same task, so APO is a plausible corrective mechanism when weight updates are unavailable. In the small exploratory trial here, this was tested on two models and at least one run produced a much stronger candidate. Second, large validation gains do not by themselves guarantee stable generalisation to unseen labelled posts. For that reason, a rewritten prompt cannot be treated as a silent patch; it must return to the same full-benchmark and cost-aware comparison as any alternative model.

Because test outcomes were inspected while the broader experimental sequence was still being interpreted, Table~\ref{tab:app-gepa-runs} is descriptive evidence only. It documents feasibility and risk, not a confirmed production-ready recovery result.

\section{Possible use after a provider-side model change}

If a future monitoring cycle shows a sustained and actionable degradation signal again, prompt optimisation could be used to generate an alternative prompt as one candidate beside a model switch. The practical idea is simple: if the provider model is closed and appears to have shifted, first test whether its behaviour can be nudged back toward acceptable classification performance by revising the instruction prompt. In that workflow, APO does not replace drift detection and does not bypass model comparison; it only adds another controllable recovery path when changing the prompt is operationally easier than replacing the provider model. Any revised prompt must still pass the same sealed full-benchmark and cost-aware evaluation as the model-based alternatives.

The observed March episode did not require this step because the degradation was transient rather than sustained. The GEPA runs reported here therefore sit outside the production episode. They are included only as exploratory evidence that, on two tested models, automated methods can sometimes find a better prompt candidate and thus offer a realistic response option if a future long-duration trigger occurs.
