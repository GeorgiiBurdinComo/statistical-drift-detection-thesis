\chapter{Exploratory Automatic Prompt Optimisation}
\label{app:prompt-optimisation}

\section{Purpose and protocol}

Automatic prompt optimisation (APO) is an attempted repair of the same
campaign-relevance classifier studied in the main chapters. The task, labels,
model endpoint, output schema, and parser stay fixed. Only the client-controlled
instruction prompt changes.

This makes APO conceptually separate from monitoring. Monitoring keeps the
request contract fixed and asks whether provider-side behaviour changed. APO is
an intentional intervention that creates a new model--prompt candidate, which
must return to the same benchmark and deployment comparison as any model switch.

Operationally, APO is a black-box search over prompt text. A seed prompt is
evaluated on labelled examples, the errors are converted into feedback, and the
optimiser proposes revised prompts. The runs reported here remain exploratory,
because test results were inspected during interpretation rather than reserved
for one final confirmatory decision.

\section{Exploratory GEPA runs}

The exploratory trial used GEPA (Genetic--Pareto Evolutionary Prompt
Optimisation)~\cite{agrawal2025gepa}. Here, a candidate is one version of the
campaign-relevance instruction prompt. The seed prompt already defines the task
and required boolean output; GEPA only rewrites that instruction.

The public repository
\url{https://github.com/GeorgiiBurdinComo/llm-batch-eval}
stores the frozen split manifest under \texttt{prompt\_optimization/splits/}
and the run-level GEPA summaries under \texttt{prompt\_optimization/runs/}.
Exact prompt text is intentionally withheld from the public branch.
\provref{P6}

GEPA evaluates a parent prompt, turns its mistakes into textual feedback, and
proposes revised prompts. Each offspring is another candidate classifier for the
same task. GEPA also keeps a small population of validation-strong prompts
instead of collapsing immediately to one incumbent.

Two runs used the same \(719/239/241\) train/validation/test split. Both validation-selected prompts improved validation accuracy, but their descriptive test outcomes differed:

\begin{table}[htbp]
\centering
\small
\caption{Exploratory prompt-search outcomes.}
\label{tab:app-gepa-runs}
\begin{tabular}{lrrrrr}
\toprule
Model & Seed val. & Best val. & Seed test & Best test & Test change \\
\midrule
\texttt{gpt-4.1-nano} & 0.766 & 0.795 & 0.784 & 0.768 & \(-1.7\)pp \\
\texttt{gpt-5.4-nano} & 0.778 & 0.954 & 0.751 & 0.929 & \(+17.8\)pp \\
\bottomrule
\end{tabular}
\end{table}
\provline{P6}

The two outcomes move in opposite directions. APO can therefore improve the same
task on a closed API model, but large validation gains do not guarantee stable
test performance. A rewritten prompt is another candidate, not a silent patch,
and must return to the same full-benchmark and cost-aware comparison.

Table~\ref{tab:app-gepa-runs} is descriptive evidence only. It shows feasibility
and risk, not a confirmed production-ready recovery result.

\section{Possible use after a provider-side model change}

If a future monitoring cycle shows a sustained and actionable degradation,
prompt optimisation could generate one recovery candidate beside a model switch.
It does not replace drift detection or model comparison. It adds one more
controllable response when changing the prompt is operationally easier than
replacing the provider model.

The observed March episode did not require this step, because the degradation
was transient. The GEPA runs therefore sit outside the production episode and
remain exploratory evidence only.
