\chapter{Exploratory Automatic Prompt Optimisation}
\label{app:prompt-optimisation}

\section{Concept and search procedure}

Automatic prompt optimisation (APO) treats a hard prompt as a discrete object that can be searched rather than edited manually. Starting from a seed prompt, an optimiser evaluates the model on labelled examples, identifies errors, proposes one or more rewritten prompts, scores the candidates, retains promising variants, and repeats until a call or cost budget is exhausted. The deployable result remains an ordinary prompt string; model weights and provider internals are not required.

The data should have three separate roles. Training examples and their errors may be exposed to the optimiser when it generates revisions. Validation examples select among the generated candidates. A sealed test set is used once after selection to estimate whether the chosen prompt generalises. Reusing test results to guide further search turns the resulting test accuracy into an exploratory rather than confirmatory quantity.

\section{Exploratory GEPA runs}

The trial used GEPA (Genetic--Pareto Evolutionary Prompt Optimisation)~\cite{agrawal2025gepa}. GEPA evaluates a parent prompt on a minibatch, constructs textual feedback from its errors, and asks a reflection model to generate an edited offspring. It retains a population of prompts that solve different validation examples well instead of immediately collapsing the search to one average-best prompt. This can preserve useful alternatives when one revision fixes some items but breaks others.

Two runs used the same \(719/239/241\) train/validation/test split. Both validation-selected prompts improved validation accuracy, but their descriptive test outcomes differed:

The \texttt{gpt-5.4-nano} result shows that automatic rewriting can produce a materially better model--prompt configuration. The \texttt{gpt-4.1-nano} result shows the opposite limitation: a prompt can look better on validation data yet generalise worse than its seed. APO therefore generates candidates; it does not guarantee improvement. In these experiments, test results were inspected while the wider experiment sequence was still being assessed, so the values above are descriptive and do not provide an unbiased confirmatory comparison.

\section{Possible use after a provider-side model change}

If monitoring detects that an API model's observable behaviour has changed, prompt optimisation could in principle be used to retune the controllable prompt for the new model state. The optimiser would generate revisions from a separate labelled adaptation set, select only on validation data, and return the selected prompt as a new deployment candidate. That candidate would still need comparison on a sealed evaluation set under the same predictive-error and inference-cost rules as a model-switch candidate.

This is a possible extension, not a result established by the monitoring study. The GEPA runs were not triggered by the observed March alert and were not applied to the degraded model state. Demonstrating automatic recovery would require a sustained changed regime, a pre-specified search protocol, no test leakage, and prospective comparison among prompt adaptation, model switching, and retaining the current configuration.
