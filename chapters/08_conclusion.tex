\chapter{Conclusion}
\label{chap:conclusion}

This thesis establishes a two-stage decision framework for external LLM
classifiers:
\begin{enumerate}
    \item a fixed monitoring panel answers whether behaviour changed;
    \item a full-benchmark comparison answers which candidate should be deployed
    for a stated business scenario.
\end{enumerate}

\paragraph{RQ1: How can campaign-relevance classification by an external LLM API
be formalised as repeated evaluation of a non-stationary black-box binary
classifier?}
Campaign-relevance classification by an external LLM API can be formalised as
repeated evaluation of a non-stationary black-box binary classifier on fixed
labelled items. The observable object is the binary output produced under a
fixed client-controlled request contract, while the provider-side state remains
hidden.
This supports a clean separation between the production task, the full
benchmark used for candidate comparison, and the frozen monitoring panel used
for repeated paired checks.

\paragraph{RQ2: How can a reduced monitoring subset be constructed and sized so
that routine evaluation is substantially cheaper while retaining sensitivity to
behavioural change?}
The monitoring subset should be a disagreement-enriched panel that
concentrates evaluation effort on difficult cases. In this thesis, exact power
analysis supports an implemented size of \(n=300\), with
\(\operatorname{Power}(300)\approx 0.80\) under the stated planning model.
The result is a low-cost warning panel for routine paired monitoring.
Production-accuracy estimation stays outside its scope.

\paragraph{RQ3: Which paired statistical test provides an appropriate rule for
detecting directional degradation across repeated runs?}
The appropriate paired test is the exact one-sided McNemar test, because the
same labelled posts are observed in both runs and the monitoring question is
directional.
The operational rule in this thesis uses nominal pairwise signals
on the fixed panel to open review. Over the recorded window, this rule
produced three nominal monitoring signals, including a temporary 12.5
percentage-point drop for \texttt{gpt-4.1-mini} from 15 to 22~March~2026
\((n=296,\ b=49,\ c=12)\) that reversed in the next run.

\paragraph{RQ4: How should candidate models be compared and selected when
predictive quality, inference cost, and campaign-specific false-positive and
false-negative costs differ?}
Candidates should be compared on common full-benchmark cases by mean inference
charge plus weighted false-positive and false-negative loss:
\[
L_t(m)
=
c_t(m)
+
\frac{
    C_{\mathrm{FP}}\mathrm{FP}_t(m)
    +
    C_{\mathrm{FN}}\mathrm{FN}_t(m)
}{n_t}.
\]
Equivalently, with
\(
w=C_{\mathrm{FN}}/C_{\mathrm{FP}}
\)
and
\(
\lambda=C_{\mathrm{FP}}+C_{\mathrm{FN}},
\)
the rule can be written as
\[
L_t(m;w,\lambda)
=
c_t(m)
+
\frac{\lambda}{1+w}
\frac{
    \mathrm{FP}_t(m)+w\mathrm{FN}_t(m)
}{n_t}.
\]
The winner depends on the declared business penalties, so the deployment rule
must rank candidates by scenario-specific loss rather than by accuracy or API
price alone.

\section{Contribution and limits}

The main contribution is a concrete decision pipeline:
\begin{itemize}
    \item a fixed client-controlled request contract and stable item identifiers
    make repeated pairing possible;
    \item exact paired testing supplies nominal review signals on the fixed panel;
    \item the full benchmark supports scenario-specific candidate selection.
\end{itemize}

The main limits are material:
\begin{itemize}
    \item the panel is a disagreement-enriched sensitivity set, therefore does
    not provide a valid accuracy estimate itself.
    \item the error prices are scenario inputs.
\end{itemize}

Future work should:
\begin{itemize}
    \item test Automatic Prompt Optimisation as a recovery path after a
    sustained monitoring signal;
    \item compare APO with other automatic candidate-generation methods, so the
    review step can propose alternatives automatically when behaviour changes.
\end{itemize}

The public code repository for the evaluation pipeline and frozen
reproducibility inputs is
\url{https://github.com/GeorgiiBurdinComo/llm-batch-eval}
